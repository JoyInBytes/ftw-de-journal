## What I learned

Each check needs a clear rule and an expected result.

| Result | Simple meaning | Example |
| --- | --- | --- |
| PASS | The data meets the rule. | Every required ID has a value. |
| WARNING | There is an issue to review. Whether we continue depends on the agreed rule. | An optional field has more missing values than expected. |
| FAIL | An important rule was broken. The issue needs action before the affected data is used. | A required ID is missing. |

SQL lets me describe checks on tables. Spark helps process large amounts of data and can also run SQL, so they can work together.

Checks should happen throughout the pipeline.

## Problem and solution

**Problem:** I initially treated all data issues as equally serious.

**Solution:** I used clear rules to decide which issues were acceptable, which needed review, and which should stop the affected work.

## Notes to remember

- The team needs to agree on each rule and how serious a failure is.
- A threshold is the limit a check uses to decide whether a result is acceptable.
- Record important failures and tell the person responsible for that part of the pipeline.
